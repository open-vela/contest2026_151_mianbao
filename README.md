## 一、作品简介

**一句话**：按下板子上的一个键，就能完成一轮完整的语音面试问答 —— 端侧录音、云端识别与大模型追问、再把"面试官"的话播回板子上，全程不用碰电脑。

**它解决什么问题**：面试练习的瓶颈是"没人陪我练"。真人模拟面试成本高、时间难约；对着镜子练又没有反馈。这个作品把面试官放进一块巴掌大的开发板里：**按一下 K1，说话，松手就自动收尾**，几十秒后面试官会用语音回应你、追问你，并给出点评。

**端云链路**：

```
        ┌─────────────────── 开发板（openvela / NuttX，全志 R528）───────────────────┐
        │                                                                         │
  K1 ──▶│ 录音(DMIC) ──▶ 静音检测自动收尾 ──▶ base64 WAV ──▶ libcurl ──┐           │
        │      ▲ LED1 快闪              ▲                             │           │
        │      │                        │                             ▼           │
        │   LED 状态机              LED1 慢闪(上传)            POST /api/interview │
        │      │                                                      │           │
        │ 播放 ──▶ LED2 常亮 ◀── base64 PCM 音频 ◀──────────────────────┘           │
        └──────────────────────────────────────┬──────────────────────────────────┘
                                               │  HTTP
                                    ┌──────────▼──────────┐
                                    │  Flask（云端服务）   │
                                    │  ASR ─▶ LLM ─▶ TTS  │
                                    │  （小米 MIMO API）   │
                                    └─────────────────────┘
```

**亮点**：

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **真机端到端跑通** | 健康检查 → 录音 → ASR 原文正确 → 多轮上下文 → TTS 播放，全链路在 DshanPI 开发板上实测通过 |
| 2 | **完整的物理交互** | 只用 2 个按键 + 2 个 LED，不依赖屏幕与串口；`main()` 常驻，随时按键开一轮 |
| 3 | **静音自动收尾** | 边说边判 RMS，说完自动停下（门限 900），不必等满计时上限 |
| 4 | **不必重烧就能调** | 面试岗位、静音门限、录音上限、服务器地址都可用 NSH 环境变量在运行期覆盖 |
| 5 | **错误的可读化** | 网络/解析/云端缺 key 等失败路径都给出中文可读提示，不吐裸错误码 |
| 6 | **问的问题有出处** | 云端内置 **2830 道真实面试题**（`question_bank/`，AI 侧 6 个岗位）与一套面试纪律方法论；每轮按岗位与回答关键词取 3 道参考题注入提示词 —— 面试官问的不是模型现编的题目，见 4.2.2 |

## 二、选题方向

**AI 硬件产品创新**。

选它的理由：这个作品的价值不在"又一个聊天应用"，而在**把大模型塞进一个专用形态的硬件**里 —— 一块开发板 + 一个按键，就是一台面试练习机。端侧负责它最擅长的事（实时采集、状态反馈、低延迟播放），云端负责它最擅长的事（识别、推理、合成），中间的边界（什么时候开始录、什么时候算说完、断网了怎么办）才是硬件产品真正要解决的问题。这些边界问题我们在这次开发里逐个踩过并落地成了代码里的判断，详见 `documents/progress_audit_2026-09-11.md`。

## 四、运行方式

复现分三步：**拉工程 → 起云端 → 编板子**。下面每一步都写清了命令与判断成功的依据。

### 4.0 从零复现：照着做的顺序

> **一律从官方仓拉取。** 本仓是 `open-vela/contest2026_151_mianbao` 的 fork，**组员与评委请从官方仓拉** —— manifest 里 `openvela.xml` 的 remote 是**相对路径** `fetch="../open-vela/"`，只有在官方仓的地址下才会解析成 `https://github.com/open-vela/`；换成别的地址（比如某个 fork）会解析到一个不存在的 org，`repo sync` 直接失败。

| # | 步骤 | 命令 / 位置 | 判断成功的依据 |
|---|------|-------------|----------------|
| 1 | 拉取全量工程 | 见 4.1 | 工作区里 `contest2026_151_mianbao/` 与 openvela 全量源码并列 |
| 2 | 起云端服务 | 见 4.2 | TTS 自检输出 `key OK, <数字> 字符 base64`；启动日志有 `[题库] 就绪：2830 道题`（少了这句 = 参考题静默失效，见 4.8-6） |
| 3 | 编译固件 | 见 4.3 | `nuttx/nuttx.bin` 时间戳刷新 |
| 4 | 打包镜像 | 见 4.3（lichee 流程） | `out/r528s3/velaevb1_nand/*.img` 时间戳刷新 |
| 5 | 烧录 | 见 4.4 | 串口出现 `nsh>` 控制台 |
| 6 | **板子连 Wi-Fi** | 见 4.5 | `ifconfig` 里 wlan0 拿到 `172.20.10.x` 且为 RUNNING |
| 7 | 运行作品 | 见 4.5 | LED1 常亮（IDLE），按 K1 可开始 |
| 8 | 验收全链路 | 见 4.5 | 按 K1 说一句话，几十秒后面试官语音回复 |

> ⚠️ **第 6 步是每次都要做的**：板子断电重上电后**不会自动连回热点**（本队实测确认），必须手工敲那四条 `wapi` 命令。这是复现时最容易漏、也最容易误判成"云端坏了"的一步，详见 4.5。

> ℹ️ **第 7 步之后可选**：云端自带的对话展示页可以在浏览器里实时看每轮问答（见 4.2.1），演示时比盯串口方便。它不是复现的必需环节。

### 4.2 云端服务（Flask）

```bash
cd contest2026_151_mianbao/cloud

# API key 只放在环境变量里，绝不写进代码或提交
pip install -r requirements.txt
export MIMO_API_KEY="<你的小米 MIMO API key>"
python3 app.py                      # 监听 0.0.0.0:5000
```

**判断成功的依据**：`python3 app.py` **不会打印任何 key 信息**（`API Key: sk-...` 那句 print 在 `llm_service.py` 的 `if __name__ == "__main__"` 里，只有直接跑 `python3 llm_service.py` 才走）。**要看 key 有没有读到，请打一发 TTS**（`/api/health` 不校验 key，永远返回 ok，**不能**用它自检）：

```bash
curl -s -X POST http://127.0.0.1:5000/api/test/tts \
  -H 'Content-Type: application/json' -d '{"text":"自检"}' \
  | python3 -c "import sys,json; a=json.load(sys.stdin).get('audio',''); print('key OK, '+str(len(a))+' 字符 base64' if a else '⚠️ audio 为空 —— key 没读到')"
```

输出 `key OK, <数字> 字符 base64` 即正常（实测约 82000~102000 字符）。

| 接口 | 方法 | 用途 |
|------|------|------|
| `/api/health` | GET | 健康检查，端侧启动即可自检 |
| `/api/interview` | POST | 主链路：上传 base64 WAV，返回文本 + base64 音频（协议见 `documents/api_protocol.md`） |

> ⚠️ **忘了设 key 的典型症状**：接口返回 HTTP 200，但端侧播不出声，串口打印「`tts_audio` 为空（云端多半缺 API key）」。**见到这条先查 key，不要查网络。**

#### 4.2.1 对话展示页 + 历史（只读）

云端自带一个网页，把面试对话实时显示成聊天气泡 —— 演示时比盯串口方便得多。**4.2 启动 Flask 后，用浏览器打开下面任一地址即可**：

| 浏览器在哪 | 打开这个地址 | 本队实测 |
|---|---|---|
| **Windows 宿主机** | `http://127.0.0.1:5000/` | ✅ 已实测可通（9/14） |
| 虚拟机桌面 | `http://127.0.0.1:5000/` | ✅ |
| 热点上的其他设备 | `http://172.20.10.2:5000/` | 未实测 |

**演示时怎么用**：先在宿主机浏览器打开 `http://127.0.0.1:5000/`（此时显示「等待面试开始」），再去按板子的 K1 开始面试 —— 对话会一轮轮自动出现。不需要任何刷新操作。

> 页面左侧是**面试官**、右侧是**候选人**；顶部显示岗位与当前轮次。面试全程**没有任何按钮需要点**。

**面试结束后面板会多出一张报告卡片**（2026-09 新增）：顶栏出现「已结束」标记，下方多出一张卡片，上半是**评分区**、下半是**两个下载按钮**：

| 卡片内容 | 说明 |
|---|---|
| **总分 + 四个维度** | **技术正确性 / 深度与原理 / 工程与场景思考 / 表达与结构**，各 0~10，带进度条、评语与"依据"（引自你原话）。⚠️ 这四个维度**与报告正文念的是同一套**（2026-10-01 统一，此前是三套并存，见台账 §11.34）。**这张卡在报告出来十几秒后才出现** —— 评分是后台另起一次调用算的，刻意不拖慢板子（见 `cloud/README.md` §3.9） |
| **逐题复盘**（默认折起来，点开才展开） | 每一题给「面试官问的 / 你的原话 / **更好的答法**」。这是整份反馈里最像"练习工具"的一节 —— 总分只说明现状，这一节才告诉你下一遍该怎么答（2026-10-01 新增，借鉴自 `myagent`） |
| `导出 Markdown` / `导出 JSON` | 给人读的（能直接贴进笔记）/ 给以后做纵向对比的（整场对话 + 结构化字段）|

> ⚠️ **报告正文不在卡片里** —— 它就是上方最后一条「面试官」消息。卡片只负责"这场结束了"、评分和拿走报告的入口；正文复制一份到卡片里迟早会出现两处不一致。

**看更早的场次：`http://127.0.0.1:5000/history`**（2026-10-01 新增）

列出**最近 20 场**，每条显示：时间 · 岗位 · 轮次 · 总分 · **首句回答**：

```
AI 应用开发        今天 15:00              2 轮 · 32 分
我用向量数据库做检索，召回率提升到 92%。
```

点任意一条 → 跳到 `/?session_id=…` 看那一场的完整对话与报告；顶栏右侧的「历史」/「← 历史」在两个视图之间来回。

> **为什么要有"首句回答"这一行**：这台设备是**公共**的 —— 一天可能有好几个人用过，那"最近一场"到底是谁的？光看时间只能定位到"大概"，**得靠"我说过什么"来认领**。这是这个功能存在的真正理由，不是为了"功能全一点"。
>
> 三个视图（`/` 最近一场 · `/?session_id=x` 指定场 · `/history` 列表）靠**真实路径 + 查询串**区分，不用前端 hash 路由 —— 这样 URL 能收藏、刷新后停在原处，方便把网址印在设备旁边。

> ⚠️ 列表页**每 5 秒刷新一次**（别人刚面完，过来看的人应该立刻看到它）；`/` 那个实时视图仍按 2 秒轮询。两者**互斥**：进列表就不拉实时会话，免得两个视图抢同一块地方。

**不打板子也能试：`http://127.0.0.1:5000/text`**（2026-10-01 新增）

一个**文字演练**入口：选岗位 → 开始 → 打字回答 → 一样出报告、评分、逐题复盘。

> ⚠️ 它是**降级通道，不是正式用法** —— 面试练习的核心是"开口说"，打字练不出语速、卡壳和口头语。页面上有一条黄条写着同样的话。
>
> 两处便利值得知道：**只打 LLM、不打语音**（成本约为 PC 排练的 1/4，板子不在手边也能验完整条链路）；**岗位可以在页面上选**（题库里那 6 个都在）—— 这是整个产品里唯一能换岗位的地方，板子的岗位是编译进固件的，换要重烧。
>
> 它产生的记录和板子那几场**并列在 `/history` 里**，用同一套会话机制、同一套报告与评分（见 `cloud/README.md` §3.10）。
>
> 导出的文件由 `GET /api/export/<session_id>?format=md|json` 生成，**内存优先、磁盘兜底**：写完报告就落盘了，Flask 重启过也能把上一场导出来。
>
> 📌 **这张卡片在 2026-09-30 之前一直是看不见的** —— 一个 CSS/JS 的写法问题（`style.display = ""` 清掉行内样式后，CSS 里的 `display:none` 重新生效），接口、DOM、CSS 全对，只有人打开浏览器才看得出来。同一批还修了"有新消息 ↓"按钮的同一个毛病（它从写出来那天起就没显示过）。详见台账 §11.33。

```bash
# 不开浏览器也能导出（把 <session_id> 换成实际会话号）
curl -sO "http://127.0.0.1:5000/api/export/<session_id>?format=md"
curl -s  "http://127.0.0.1:5000/api/export/<session_id>?format=json" | head -20
```

页面每 2 秒拉一次 `GET /api/history`，全程只**读**不写：

- 不创建、不修改、不污染会话 —— 板子那场面试完全不受影响；
- 刻意**没有**"发消息"输入框（那会让网页也去调 `/api/interview`、多出一个 session，演示时误触就会把板子那场搅乱）；
- 页面不引用任何外部 CDN，手机热点没外网也能正常显示。

**实测**（PC 端 11 轮真实对话 + 页面每 0.5 秒疯狂轮询）：板子链路 11 轮全部 HTTP 200、0 兜底文案；网页轮询 **295 次 0 失败**、平均 2.4ms、最大 11.6ms，期间板子链路无一次超时 —— Flask 默认是多线程的，网页不会把板子堵住。

> **看到多条重复的"你好，我是 AI 模拟面试官…"是正常的** —— 那是用同一个音频文件反复测试造成的，不是页面在重复渲染。真实面试每轮内容不同。

#### 4.2.2 题库与方法论 —— "问的问题有出处"

云端**不是**把候选人的话丢给大模型让它自由发挥。每一轮它都先从内置题库里取出几道与**岗位**、与**你刚说的那句话**相关的真实面试题，作为参考注入提示词。

**题库**（`question_bank/`，2830 道，AI 侧 6 个岗位）：

| `role` 取值 | 题数 | 出处 |
|---|---|---|
| `AI 应用开发` | 748 | 中文侧：开源面试题库（JavaGuide / CS-Notes 等）+ Hugging Face 中文面试数据集 |
| `AI Agent 开发` | 315 | 同上 |
| `大模型算法工程师` | 120 | 同上 |
| `AI/ML Engineer` | 576 | 英文侧：公开 ML 面试数据集 |
| `Data Scientist` | 495 | 同上 |
| `Data Analyst` | 576 | 同上 |

题目来源、字段表、与上游数据的 3 处差异、已知局限，全部写在 **[`question_bank/README.md`](question_bank/README.md)** —— 那份说明是题目出处的**唯一**记录（本仓没有逐条标注来源）。

**每轮取题怎么走**（`cloud/question_bank.py`，纯标准库、无随机数、可复现）：

1. `role` 先归一化（NFKC + 去空白引号 + 转小写），再依次走「精确命中 → 别名表 → 双向包含取最长」映射到真实岗位（例如 `算法工程师` → `大模型算法工程师`、`AI 应用开发工程师` → `AI 应用开发`）；
2. 从候选人**最近一句回答**里抽关键词（英文按词、中文按二字组），在题库里做关键词检索；
3. 关键词没命中就按**类别轮换** —— 类别顺序有固定优先级：系统设计/架构 → Python/编码/基础原理 → 沟通/协作，其余再按字母序。**这条优先级不是装饰**：早先版本纯按字母序轮换，`Python` 排在 24 个类别的第 13 位，10 轮里根本轮不到，方法论要求的"至少问到一道编码/基础原理题"落不了地；
4. 历史里已经问过的题会被排除（比对面试官发言），同轮不重复。

取出的 3 道题拼成一段**参考块**，注入 `next_question` 的 system prompt。**参考块只进 system prompt，绝不进 history** —— 让模型在历史里看到自己问过的题，等于递给它一份"范例"去模仿，它会越写越长且自我强化（本项目踩过的坑，见台账 §11.20）。

**方法论**：提示词里另有一段【面试纪律】，取自同作者的开源项目 **myagent** 的 mock-interviewer：一次只问一个问题、不给即时反馈、顺着回答钻细节追问、同一话题最多追 2 轮、避开"你最大的缺点是什么"这类无信息量的问题。报告端同样改成固定的"四维度 + 引用原话"（见 `skills/README.md` §3.2 / §3.4）。

**最后一道闸**：模型偶尔会在长会话里"跑偏"，把推理过程当正文写出来（`判断：追问细节 / 理由：…`，见台账 §11.20）。这段文本会被 TTS **逐字念出来**，所以 `cloud/reply_guard.py` 在**出口**（返回前）和**入口**（读历史时）各剥一遍，只留下要对候选人说的话；剥空了就顶上兜底问句。提示词层面也禁了，但实测**光靠提示词挡不住**被污染的历史，闸门才是那条确定的底线。

> **退化行为（要会读）**：岗位名对不上题库、或题库目录没随代码拷过去时，参考块为空，提示词退化成"没有题库"的样子 —— **面试照常能跑，只是问的问题不再有出处**，界面上没有任何报错。所以演示前必须确认启动日志里那行 `[题库] 就绪：2830 道题`，见 4.8 关卡 6/7。

### 4.5 板子连网、上板运行与交互

#### 4.5.1 先让板子连上热点（**每次上电都要做**）

板子**不会自动连回热点**（本队实测确认）。上电后第一件事：

```
nsh> ifconfig
```

wlan0 拿到 `172.20.10.x` 即已连上。**没拿到就手工重连**（数字索引已对着源码核实）：

```
nsh> wapi mode  wlan0 2
nsh> wapi psk   wlan0 <热点密码> 3
nsh> wapi essid wlan0 <热点名>   1
nsh> renew wlan0
```

| 参数 | 值 | 含义（`apps/wireless/wapi/src/wireless.c`） |
|------|-----|------|
| `mode` | `2` | `WAPI_MODE_MANAGED` —— 站点（STA）模式 |
| `psk` | `3` | `WPA_ALG_CCMP` —— WPA2-AES，现代热点的标准选项 |
| `essid` | `1` | `WAPI_ESSID_ON` —— 立即生效，不延迟绑定 |

**顺手关掉 Wi-Fi 省电**（强烈建议）：

```
nsh> wapi power_save wlan0 off
```

Realtek 的省电模式是 wlan0 随机掉线的头号嫌疑（驱动进省电后可能漏收信标，被 AP 判为离线踢掉），而 **wlan0 掉线是本项目所有端到端失败的共同根因**。该命令的实现是「参数恰好等于 `on` 才开，其余一律关」，写 `off` 一定能关掉。

> ⚠️ **`wapi save_config` 和 `wapi reconnect` 在本板固件上不存在**（敲了会报错）。它们被 `#ifdef CONFIG_WIRELESS_WAPI_INITCONF` 包着，而本板该配置为**关** —— 所以**没有"存下来下次自动连"这回事**，只能每次手工敲上面四条。要启用需改 vendor 树的板级 `defconfig` 并整个重烧，本队评估后认为不值得。

#### 4.5.2 运行

```
nsh> ai_interview
```

> ⚠️ `main()` 是 `for(;;)` 常驻循环，**跑起来后 NSH 不会再回到 `nsh>` 提示符**，敲什么都没反应 —— 这**不是卡死**。要重新跑只能复位板子。

**交互**（看 LED 就知道它在干什么）：

| 操作 / 状态 | LED 表现 |
|-------------|----------|
| 待机（IDLE） | LED1 常亮 |
| 按 **K1** 开始一轮 | LED1 快闪（亮 200ms／灭 200ms，录音中）→ 说完自动收尾 |
| 上传与云端处理 | LED1 慢闪（亮 800ms／灭 800ms）—— 与快闪差 4 倍，一眼能分 |
| 播放面试官语音 | LED2 常亮 |
| 按 **K2**（录音／上传／播放中） | 取消当前一轮，回到 IDLE |
| 按 **K2**（错误态下） | 回到 IDLE |
| 按 **K2**（待机下） | **无操作** —— 待机时没有可取消的东西 |
| 出错 | LED1 三短闪（亮 100ms×3）后停 600ms，循环 |

（K3 已初始化但功能未实现，按键动作只打日志。）

> ⚠️ **快闪与慢闪的差别是 2026-09-30 才真正做出来的**：在此之前两个分支写的是同一段
> “每次调用翻转一次”的代码，而主循环固定 100ms 调一次 —— 于是录音与上传**闪得一模一样**，
> 表里写的 200ms/800ms 只是注释里的愿望。同一批还修了 **K2 在待机态会卡死录音**：
> 原来靠 `!busy` 反推状态、误以为"不忙碌 = 停在错误态"，而待机同样不忙碌 → 按一下 K2
> 状态机就被推进 RECORDING，工作线程却没收到 `CMD_START`，整机停在"录音中"（LED1
> 快闪、其实什么都没录）且没有任何超时能救。详见台账 §11.26。

#### 4.5.3 一轮面试的完整逻辑（何时结束、报告从哪来）

**一次 K1 的完整链路**：

```
K1 → 录音（静音 2 秒自动收尾，最长 30 秒）→ 上传 → 云端 ASR
   → LLM（题库参考题 + 面试方法论）→ 回复闸门 → TTS → 端侧播放 → 回 IDLE
```

**多轮**：板子每轮**只带上 `session_id`**，**对话历史完全由云端维护**——端侧请求体里的 `history` 恒为空数组（`app/ai_interview/network_client.c` 内有注释说明）。`session_id` 在第一次请求时由云端生成，之后由端侧持有并回传。会话与历史都在云端进程内存里，并且**每轮结束时落一份到磁盘**（`cloud/data/sessions/<session_id>.json`，2026-09 新增）——重启云端不再等于"上一场没了"，网页和导出接口照样能取到它。

**这 10 轮是有形状的**（2026-10-01 起，`cloud/interview_stage.py`）——不是"一直问到够数"，而是按真实面试的推进走：

| 第几轮 | 阶段 | 面试官这一段在干什么 |
|---|---|---|
| 第 1 轮 | **开场** | 接住他的自述，请他挑一个项目讲具体 |
| 第 2~3 轮 | **背景深挖** | 顺着那个项目往下钻：职责 / 指标 / 选型 / 结果 |
| 第 4~9 轮 | **技术问答** | 从题库取题问（**只有这一段注入参考题**） |
| 第 10 轮 | **反问** | 「你有什么想问我的吗」——这句本身就是"快结束了"的信号 |
| 第 11 轮 | **收尾** | 回应他的反问 → **评估报告** |

> **代码决定"现在处于哪一段"，模型决定"这一段里问什么"。** 不让模型自己数轮次 —— 它数不准。
>
> 最直观的改善在结尾：第 10 次按 K1 听到的是"你有什么想问我的吗"，而不是"又一道题"。

**结束有两条路径，判据都在云端**（端侧固件没有参与，**无需重烧**）：

| 第几次按 K1 | 云端走的分支 | 候选人听到 |
|---|---|---|
| 第 1 ~ 10 次 | `next_question`（按上表分五段） | 问题 1 ~ 10 |
| **第 11 次** | `generate_feedback` | **评估报告** |
| 任意一轮说了结束语 | `generate_feedback` | **评估报告**（当场收尾，不必按满 11 次） |

* **主路径 —— 云端自己数轮次**：`len(history) - 1 >= HISTORY_FINISH_THRESHOLD`（`cloud/llm_service.py`，阈值 = 20 条消息 = 10 个问答对）。**演示请走这条：答满 10 轮（走完五段），第 11 次按 K1 即为报告。**
* **辅路径 —— 候选人明确要求结束**（2026-09 云端新增）：说「结束吧」「谢谢老师，我没有其他问题了」这类话，云端也直接出报告。识别在 `cloud/finish_guard.py`，判据刻意保守，四道闸：归一化（全角转半角、去标点、转小写）→ 长度 ≤20 字 → 不含问号 → 剥掉「好的 / 谢谢老师 / 嗯」这类首尾客套后，核心必须命中短语白名单。**宁可漏判，绝不误判**：漏判只是回到主路径（继续问、最后按轮次出报告），误判是把面试当场掐断。

> ⚠️ **「没问题」「可以了」「就这样吧」「没了」故意不在白名单里** —— 它们在技术回答里都太正常（"这个问题没问题"），而误判代价远大于漏判。同理，「先别结束，我还想补充一点」「结束了吗？」「循环结束的时候会释放资源」都不会被误判。
>
> ⚠️ 语音结束走的是**云端的 ASR 转写结果**，不是端侧的关键词匹配（端侧根本没有关键词识别）。ASR 把话说劈了就会漏判 —— 所以它是辅路径，演示请按主路径走。

**报告播放完之后**：端侧打印 `[Main] 本轮面试结束（next_action=finish）`，**清空本地 `session_id`** 并回到 IDLE（LED1 常亮）。此时**再按 K1 就是一场全新面试**（云端新会话、历史清零），不需要重启云端。

**异常路径**（均不中断整场面试）：

| 情况 | 行为 |
|------|------|
| 整轮静音 / ASR 没识别出字 | 短路回一句「抱歉，我没听清，请再说一次。」，**不进 LLM**、**也不进历史** —— 防止模型在无输入时自由发挥把响应体撑爆端侧 8MB 缓冲；不进历史是为了不打乱轮次计数（一次静音轮曾把报告从第 11 次 K1 推迟到第 12 次） |
| LLM 调用失败 | 该轮回兜底文案（问句为「抱歉，生成问题失败，请重试。」，报告为「生成报告失败」），面试可继续 |
| 岗位对不上题库 | 静默退化：照常提问，只是不再注入参考题（见 4.8 第 7 条） |
| 按 K2（本轮进行中） | 取消当前一轮，回 IDLE；待机时按它**无操作**（见 4.5.2 的表） |

### 4.6 网络地址（CLOUD_URL）

云端地址**默认编译进固件**：`http://172.20.10.2:5000`。

- 这个默认值对应「**手机热点**」的拓扑：板子连热点（`172.20.10.x`），iPhone 热点网段固定为 `172.20.10.0/28`，而**云端就跑在宿主机上，地址正是 `172.20.10.2`** —— 不用改任何配置。
- ⚠️ **机器上如果还留着老的 VMware 端口转发规则，必须先删掉**（2026-09-30 实测踩到）。比赛期为了让虚拟机里的 Flask 被板子访问，曾在 VMware NAT 里配过一条 `5000 = 192.168.93.141:5000`；它是**持久配置**，虚拟机都关机了它还在 —— `vmnat.exe` 会和你新起的 Flask **抢同一个端口**，把板子的请求转给一台已关机的虚拟机。症状是最难查的那种：**服务端看着一切正常，板子却报"云端不可达"**。

  删法：VMware → 编辑 → 虚拟网络编辑器 → 更改设置（需管理员）→ VMnet8 → NAT 设置 → 端口转发 → 删掉 5000 那条。删掉的只是**入站转发**，VM 的上网（NAT 出站）不受影响。详见台账 §11.27。
- 换网络（例如安卓热点 `192.168.x.x`）时可运行期覆盖，无需重烧：

  ```
  nsh> set CLOUD_URL http://192.168.1.23:5000
  ```

  环境变量优先于编译期默认值。**2026-09-30 已在真机上正面验证**（此前"未验证"的悬案见台账 §11.28）：板子连热点拿到 `172.20.10.5`、`set CLOUD_URL http://192.168.1.11:5000`（一个板子当时**够不到**的地址）之后，启动时的健康检查**如期失败** —— 而同一个板子用编译期默认地址是连得上的，两相对照即证明覆盖确实生效。

  **怎么一眼看出用了哪个地址**：启动时会打印两行（2026-09-30 起由**主线程**打印，不再是工作线程，因此不会被串口吞掉）：

  ```
  [Cloud] 云端地址: http://172.20.10.2:5000
  [Cloud] 来源: 编译期默认值（CLOUD_URL 未设或不合法）
  ```

  第二行会明确告诉你 `set CLOUD_URL` **到底生效没有** —— 在有这两行之前，那行打印被主线程的输出踩掉过两次（NuttX 的 stdio 非线程安全，见 4.8 第 4 条），害得当时只能用"故意指一个够不到的地址"这种绕法来判断（台账 §11.28）。

  > 如果你的固件是 2026-09-30 之前烧的，那还只有老的那行 `[Cloud] 云端接口: …`，**且它可能不出现** —— 那种情况就靠**连接成不成功**来判断。

### 4.7 运行期可调参数

演示时改岗位、调灵敏度都不必重烧，全部走 NSH 环境变量（设定后再启动 `ai_interview`）：

| 变量 | 默认 | 作用 |
|------|------|------|
| `CLOUD_URL` | `http://172.20.10.2:5000` | 云端地址 |
| `ROLE` | `AI 应用开发` | 面试官岗位/角色。**取值要能对上云端题库的岗位名**，否则拿不到参考题 |
| `SILENCE_THRESHOLD` | `900` | 静音门限（RMS，16bit 满幅）。低于它视为"说完了" |
| `MAX_REC_SEC` | `30` | 单轮录音上限（秒），到点强制收尾 |
| `PCM_DEV` | `hw:snddmic` | 采集设备名（本板麦克风是**数字麦 DMIC**） |
| `MIC_GAIN` | `4` | 数字增益 |

> ⚠️ **`ROLE` 里带空格，别用 NSH 的 `set` 直接覆盖它**：NSH 的 `set` 按空白分词，`nsh> set ROLE AI 应用开发` 只会把 `AI` 赋给变量，结果倒是**不报错**，只是岗位变成 `AI`、对不上题库、参考题静默消失。要换岗位有两条路：改 Kconfig 默认值重新烧，或者用**不含空格的别名**：
>
> ```
> nsh> set ROLE 智能体开发      # → AI Agent 开发
> nsh> set ROLE 算法工程师       # → 大模型算法工程师
> nsh> set ROLE 数据分析师       # → Data Analyst
> ```
>
> 完整别名表见 `cloud/question_bank.py` 的 `ROLE_ALIASES`。

> **门限 900 的来历**：9/13 实测安静时单块 RMS 最高 381、说话时 556~1951，当时取中间的 500；9/14 晚现场底噪升高，安静段频繁越过 500，程序便把安静当成"一直在说话"，每轮都要录到时长上限才停 —— 于是上调到 **900**。
>
> ⚠️ **这个值不是"绝对灵敏度"，而是"当前房间底噪 + 本板自噪"的匹配值，换环境就要重调。** 调法看日志里每秒一行的 `[Audio] N 秒, RMS 平均 X [最低, 最高] (门限 T), 本秒人声 P%`：**安静段必须明显低于门限**（低于才判得出"说完"），**说话段必须明显高于门限**（否则会把你说话当静音，说一半就截断）。注意判定要求**连续**静音 —— 只要有一块越过门限，倒计时就从头再来，所以要看安静段的**最高**值有没有冒头，不能只看平均。

### 4.8 复现时最容易卡住的几处

按"踩过的坑"排序，遇到问题先查这里（完整记录见 `documents/progress_audit_2026-09-11.md` 第十一节）：

1. **录音采回来全是零** → 麦克风在**数字麦**上，设备名要用 `hw:snddmic`；设备名 `default` 解析到的是模拟 codec，那条通路上没有麦克风。
2. **"连不上服务器"，但抓包里看不到板子的任何包** → **先看板子 `ifconfig` 里 wlan0 有没有拿到 IP、是不是 RUNNING**（重连命令见 4.5.1）。开发板掉出热点是本项目所有端到端失败的共同根因，重连即恢复；**不要先去查服务端或防火墙** —— Windows 防火墙从头到尾都不是原因，不必为它加规则。
3. **排查音频别用 `arecord -t`**（录完即放）—— 采集与回放会撞在同一个设备上，"采集支持 3 声道、播放只支持 1~2 声道"会**伪装成采集失败**。请 `arecord ... <文件>` 采到文件，再 `aplay <文件>` 单独放。
4. **串口输出不可全信**：这板子会截断整行、也会丢中间一段；主线程与工作线程同时打印还可能互相踩出花屏。判断运行状态**以 LED 为准**。
5. **云端 key 只在进程内存里**：`export MIMO_API_KEY=...` 没有落盘，虚拟机一重启就没了，必须重新导出（症状见 4.2）。
6. **题库没加载，面试照样能跑** —— 这是**静默**退化，不会报错、界面上看不出来。启动 Flask 时若没打印 `[题库] 就绪：2830 道题，岗位：…`，而是打了 `[题库] 未加载到题目`，说明 `question_bank/data/` 没跟代码一起拷过去（或目录被改名）。此时面试还能进行，只是不再注入参考题。**演示当天开机第一件事就是看这一行。**
7. **岗位名对不上题库 → 拿不到参考题**（同样静默）。`ROLE` 要取题库里 6 个岗位名之一（见 4.2.2 表），或别名表里的别名；写别的（比如 `产品经理`）不报错，只是参考块为空。还要注意 NSH `set` 的空格陷阱（见 4.7）。
8. **答了 10 轮也没出报告** → 报告落在**第 11 次按 K1**（完整逻辑见 4.5.3）；提前出报告只可能是候选人自己说了结束语。复现和演示都请走完那五段（10 轮）。反过来，**如果第 11 轮没出报告**，先看这轮是不是空识别短路（静音/没听清）—— 那种轮次不进历史、不计轮次，报告会顺延一次。
   另外，**如果你觉得"第 10 轮听到的怎么还是一个问题"**：那说明这一段是**反问环节**——「你有什么想问我的吗」按设计就是这一轮的收尾信号，回答完之后才是报告（见 4.5.3 的五段表）。

## 五、AI Coding 使用说明

本作品从需求拆解到上板调试全程与 AI 结对完成。比赛期按组委会要求导出并提交过对话日志（`logs/`），比赛结束后已移除，见本节末尾。

**各环节怎么用**：

| 环节 | 用法 |
|------|------|
| 需求拆解 / 方案设计 | 让它先读组委会文档与板级源码，列出可选方案与代价；**边界判断（如"什么时候算说完"）由人拍板** |
| 编码 | 状态机、网络、音频三条线的代码骨架与错误分类由 AI 起草，人审后落地 |
| 调试 | 最耗时的一环。麦克风采到全零、Wi-Fi 掉线、串口日志截断等疑难问题，都是"提出假设 → 让它去源码/镜像里找证据 → 证伪或证实"这样推进的 |
| 文档 | 工作台账、演示日恢复手册、本 README 均由 AI 依据实测结果整理 |

**密钥闸门**：`tools/redact_secrets.sh` 按特征（`sk-` + 24 位以上字母数字）扫描**全仓被跟踪的文本文件**；`tools/hooks/pre-commit` 在每次提交前自动跑一遍 `--check`，发现疑似密钥即中止提交。

⚠️ **钩子需要每个克隆手动装一次** —— 钩子从不随 `git clone` 传播，`core.hooksPath` 又只是本机配置，所以新克隆下来是**没有闸门**的。装一次即可：

```bash
git config core.hooksPath tools/hooks
```

确需绕过用 `git commit --no-verify`；也可以随时手动跑 `tools/redact_secrets.sh --check`。

这件事不多余：`MIMO_API_KEY` **真的进过 git 历史**（commit `812a1b5`、`f948ff7`，涉及 `cloud/` 下 4 个文件），之后删文件也删不掉，只能靠轮换收场。也正因为那次泄露**不在 `logs/` 里**，扫描范围在 2026-09-29 从 `logs/` 改成了全仓 —— 旧版本当初就拦不住它。

> **关于已移除的 `logs/`**：比赛期按组委会手册导出的对话日志（10 个日期、约 15MB）于 **2026-09-29 从本仓移除**，规则见 `.gitignore`。
